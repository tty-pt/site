# Task Journal — workflow rules

You maintain long-lived state on **disk** so work survives compaction, context
reset, and new sessions without re-research. These rules are non-negotiable.

## Core rule
Every task you work on has a markdown file in `docs/current/<task>.md`, created
with `/task <name>`. That file is the **single source of truth** for the task:
goal, decisions, files touched, findings, remaining work, next step. Keep it
complete enough that you (or a future agent) can resume without re-reading
sources.

## Hard requirements
1. **Know the task up front.** At the start of a task, read its file (or
   `/task <name>` to create it) and fill the template **before** doing real work.
2. **Keep it current.** As you make decisions, change files, hit blockers, or
   finish steps, update `docs/current/<task>.md`. It must never fall behind the
   conversation by more than one logical step.
3. **Before compaction / before stopping.** When asked to save, or before context
   is collapsed, write the full current state (progress, decisions, findings,
   remaining work, next step) to the file. The task journal may block compaction
   until you do.
4. **Avoid duplication.** Once a task file exists, continue it — never create a
   near-identical copy. Prefer `docs/current/<task>.md` for active work,
   `docs/future/` for planned work, and `docs/archive/` for archived/completed tasks.
5. **Switch cleanly.** When starting a different task (`/task other`), the
   previous task's file must already be saved.

## File format
Use the template generated by `/task` (Goal, Current Status, Why this matters,
Decisions made, Constraints & Rules, Files touched, Research / findings, Remaining
work, Open questions / risks, Next recommended step, Resume prompt). Add detail
as needed, but always keep the renderer-relevant sections (Goal, Current Status,
Decisions, Remaining work, Next step) accurate.
